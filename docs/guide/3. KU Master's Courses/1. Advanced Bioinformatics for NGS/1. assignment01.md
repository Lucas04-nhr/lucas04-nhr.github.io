## Part A: Exact Alignment Exercise {#exact-alignment-exercise}

Consider the text `ACGTAACGTAACGCANTAACG` and pattern `TAACG`.

::: info
I use $T$ for the text and $P$ for the pattern, and let $n$ be the length of the text $|T|$ and $m$ be the length of the pattern $|P|$.
:::

1.  What is the length of the strings, and what is the size of the alphabet?

    The text has length $n = 21$ and the pattern has length $m = 5$.

    The symbols occurring in the text are is $\Sigma = \{A, C, G, T, N\}$, so the size of the alphabet is $|\Sigma| = 5$.

2.  How many shifts and how many comparisons do we need for an exhaustive naive search?

    A pattern of length $m$ can start at $n - m + 1$ positions in the text, so we need $n - m + 1 = 21 - 5 + 1 = 17$ shifts. That is, there are **17 possible shifts/alignments**.

    If we exhaustively compare all $m = 5$ characters at every position, the number of character comparisons is $17 * 5 = 85$ comparisons. Thus the worst-case exhaustive naive search requires **17 alignments and 85 character comparisons**.

    If the implementation stops as soon as it encounters the first mismatch, the number for this particular sequence is much smaller. The three true matches each require 5 comparisons, while the remaining 14 windows differ already at the first character:

    $$
      3 \times 5 + 14 \times 1 = 29
    $$

    So an early-termination naive implementation performs only 29 character comparisons on this particular example, although its worst-case complexity remains $O(nm)$. The pattern occurs at zero-based text positions **3, 8, and 16**.

3.  Consider the Rabin–Karp algorithm and define a rolling hash function.

    We can treat a DNA string as a number in base 5, and define the character encoding as follows:

    ::: flex center center

    | Character | Encoding |
    | :-------: | :------: |
    |     A     |    0     |
    |     C     |    1     |
    |     G     |    2     |
    |     T     |    3     |
    |     N     |    4     |

    :::

    For a length-$m$ string, we have: $S = s_0 s_1 ... s_{m-1}$, and we can define the hash function as:

    $$
      h(S) = \left( \sum_{j=0}^{m-1} v(s_j) \cdot 5^{m-1-j} \right) \mod 101
    $$

    where $v(s_j)$ is the integer encoding of character $s_j$.

    For the exercise, let $m = 5$, so we have

    $$
      \begin{aligned}
        h(S) & = h(s_0 s_1 s_2 s_3 s_4) \\
             & = \left( v(s_0) \cdot 5^4 + v(s_1) \cdot 5^3 + v(s_2) \cdot 5^2 + v(s_3) \cdot 5^1 + v(s_4) \cdot 5^0 \right) \mod 101
      \end{aligned}
    $$

    ::: note
    Use of the prime modulus 101 is to keep the hash values small while reducing collisions.

    For the pattern `TAACG`, we have the encoded values `3, 0, 0, 1, 2`, so the hash value is:

    $$
    \begin{aligned}
    h(P) & = (3 \cdot 5^4 + 0 \cdot 5^3 + 0 \cdot 5^2 + 1 \cdot 5^1 + 2 \cdot 5^0) \mod 101 \\
         & = (3 \cdot 625 + 0 + 0 + 5 + 2) \mod 101 \\
         & = (1875 + 7) \mod 101 \\
         & = 1882 \mod 101 \\
         & = 64
    \end{aligned}
    $$

    :::

4.  Explain why your hash function is a rolling hash function.

    The important property is that the hash of the next window can be computed from the previous hash without recomputing all five characters.

    Suppose we have a window $S = s_0 s_1 s_2 s_3 s_4$ with hash $h(S)$, and we want to compute the hash of the next window $S' = s_1 s_2 s_3 s_4 s_5$. We can derive the rolling hash as follows:

    ::: steps
    1. The old contribution of $s_0$ is $v(s_0) \cdot 5^4$. We can remove this from the hash by subtracting it.
    2. After removing it, all remaining characters shift one base-5 position to the left, which is equivalent to multiplying by 5.
    3. The new character $s_5$ is added to the hash.
       :::

    Therefore, we have:

    $$
      h_{i+1} = \left[ 5 \left( h_i - v(T_i) \cdot 5^{m-1} \right) + v(T_{i+m}) \right] \mod 101
    $$

    For $m = 5$, we have $5^{m-1} = 5^4 = 625$ and $625 \mod 101 = 19$

    So the practical update can be written as:

    $$
      h_{i+1} = \left[ 5 \left( h_i - 19 \cdot 5^{m-1} \right) + v(T_{i+m}) \right] \mod 101
    $$

    This requires constant time, $O(1)$, per shift rather than $O(m)$.

    That's why it is a **rolling hash**.

5.  Compute the hash of the pattern and the hash of each shift. Is your choice of hash function good?

    The pattern hash is $h(P) = 64$.

    The 17 text windows and their hashes are:

    ::: flex center center
    | Position | Window | Hash |
    | -------: | :-----: | -----: |
    | 0 | `ACGTA` | 89 |
    | 1 | `CGTAA` | 41 |
    | 2 | `GTAAC` | 10 |
    | 3 | `TAACG` | **64** |
    | 4 | `AACGT` | 38 |
    | 5 | `ACGTA` | 89 |
    | 6 | `CGTAA` | 41 |
    | 7 | `GTAAC` | 10 |
    | 8 | `TAACG` | **64** |
    | 9 | `AACGC` | 36 |
    | 10 | `ACGCA` | 79 |
    | 11 | `CGCAN` | 96 |
    | 12 | `GCANT` | 85 |
    | 13 | `CANTA` | 33 |
    | 14 | `ANTAA` | 70 |
    | 15 | `NTAAC` | 48 |
    | 16 | `TAACG` | **64** |
    :::

    Therefore, Rabin–Karp identifies the three candidate positions: **3, 8, and 16**.

    All three candidate strings are actually equal to `TAACG`, so there are **no hash collisions** in this example. The hash function is therefore good for this small data set.

    However, a hash function is not judged only by this one example. A good hash function should:
    - distribute possible strings approximately uniformly over the hash space;
    - have a low collision probability;
    - be fast to calculate;
    - support an $O(1)$ rolling update;
    - distinguish changes in both character identity and character position.

    For Rabin–Karp, a useful practical metric is the **collision rate**:

    $$
      P(h(X) = h(Y) \mid X \neq Y)
    $$

    If hashes are approximately uniformly distributed over \(q\) values, we would ideally expect the collision probability to be approx. $\dfrac{1}{q}$. In this example, we have $q = 101$, so the expected collision probability is $\dfrac{1}{101} \approx 0.0099$.

    A deliberately bad rolling hash could simply be:

    $$
      h(S) = \left(\sum_i v(s_i)\right) \mod 5
    $$

    It can still be rolled efficiently:

    $$
      h_{i+1} = \left(h_i - v(T_i) + v(T_{i+m})\right) \mod 5
    $$

    However, it ignores the order of the characters. For example, `ACGTA` and `TACGA`, as well as any permutation containing the same characters have the same hash value, even though they are different strings. This is a poor hash function because it has a high collision probability.

    Another extremely bad example is $h(S) = 0$, which is constant for all strings. It technically allows constant-time updates, but every window collides with every other window, so Rabin–Karp degenerates to naive matching.

6.  How many operations did the exhaustive search with the Rabin–Karp algorithm require?

    There are 17 candidate windows.

    Rabin–Karp first computes the hash of the pattern and the first text window. The remaining 16 window hashes are generated using the $O(1)$ rolling update.

    We therefore perform 17 hash comparisons:

    $$
      h(P) \stackrel{?}{=} h(T[i:i+5])
    $$

    Only three windows have the same hash as the pattern: 3, 8, and 16.

    Because a hash match is only a candidate match, Rabin–Karp must verify these strings explicitly. Each verification requires at most 5 character comparisons: $ 3 \times 5 = 15 $ comparisons in total.

    Thus, if we count hash comparisons and verification character comparisons, $17 + 15 = 32$ operations in total. They are required after the hashes have been constructed.

    If hash-generation operations are also counted, the accounting is slightly different:
    - compute pattern hash: $O(m)$;
    - compute first text-window hash: $O(m)$;
    - 16 rolling-hash updates: $O(16)$;
    - 17 hash comparisons;
    - 15 verification character comparisons.

    Thus the important complexity is not the exact constant number but $O(n + m)$, which is much better than the $O(nm)$ of naive matching.

7.  When is Rabin–Karp beneficial?

    Rabin–Karp is especially beneficial when the text is large and the pattern is long enough that repeatedly comparing every character would be expensive.

    Its main advantage is that most candidate positions can be rejected by comparing only two fixed-size hash values when

    $$
      h(P) \neq h(T[i:i+m])
    $$

    A character-by-character comparison is needed only when the hashes agree.

    It is particularly useful when:

    ::: steps
    1.  ==**Searching a long text or genome.**==

        After the first window hash is computed, each new position can be examined with an \(O(1)\) rolling update.

    2.  ==**Searching for many patterns of the same length.**==

        Their hashes can be stored in a hash table, and every text window can be tested against many patterns simultaneously.

    3.  ==**Exact matching is required.**==

        Rabin–Karp provides candidate matches efficiently, followed by exact verification.

    4.  ==**The hash function has a low collision rate.**==

            In the expected case, only true or rare accidental hash matches require full sequence comparison.

        :::

    For sequence analysis, this illustrates a broader motivation behind efficient alignment algorithms: real NGS analysis involves mapping large numbers of sequence reads to reference genomes, and a direct exhaustive comparison against every reference position would be computationally prohibitive. The course materials therefore introduce specialized high-speed aligners such as BWA and Bowtie rather than exhaustive string comparison.

## Part B: Next-generation Sequencing Exercise {#ngs-exercise}

### Background and Aim {#background-and-aim}

Ancient DNA (aDNA) is typically characterised by **short fragment lengths**, **low endogenous DNA content**, and **post-mortem nucleotide damage**, especially increased **C→T substitutions near the 5′ end** and complementary **G→A substitutions near the 3′ end**. PCR amplification can further reduce the effective information content of a sequencing library by generating duplicate reads.

The aim of this analysis is to compare two paired-end Illumina datasets, `ex1` and `ex2`, obtained from two DNA extractions of a human-like skeleton. The analyses are designed to determine:

1. whether the sequencing data are consistent with **human origin**;
2. whether the data contain molecular signatures consistent with **ancient DNA**;
3. which extraction should be prioritised for further downstream analysis.

Initial quality control showed that **`ex1` had greater sequencing depth, lower duplication, and fewer failed FastQC modules than `ex2`**.

The principal QC differences were **the higher duplication rate and GC content in `ex2`, together with more failed FastQC modules, particularly for `ex2_R2`**. These observations were used to guide adapter trimming but were not sufficient alone to determine which extraction should be prioritised.

Post-trimming QC revealed a marked difference between the two extractions. `ex1` retained a mean read length of approximately 75 bp, whereas `ex2` decreased from ~74 bp before trimming to ~57 bp after trimming (median 59 bp), indicating substantially more adapter and/or low-quality terminal sequence in `ex2`. Sequence duplication remained low in `ex1` (~0.1%) but substantially higher in `ex2` (~8.9%), while GC content remained approximately 48% and 55%, respectively. The strong reduction in `ex2` read length is compatible with shorter DNA inserts, but ancient origin cannot be inferred from trimming alone and was therefore evaluated using mapped fragment lengths and nucleotide misincorporation patterns.

#### Read Mapping {#read-mapping}

Reads were mapped using BWA `aln` / `sampe`.

::: steps
1. Map `ex1` & `ex2` separately, following command is for `ex1` only, repeat for `ex2`.

    ```bash
    mkdir -p mapping

    bwa aln chr22.fa trimmed/ex1.pair1.truncated.gz > mapping/ex1_R1.sai
    bwa aln chr22.fa trimmed/ex1.pair2.truncated.gz > mapping/ex1_R2.sai

    bwa sampe \
      chr22.fa \
      mapping/ex1_R1.sai \
      mapping/ex1_R2.sai \
      trimmed/ex1.pair1.truncated.gz \
      trimmed/ex1.pair2.truncated.gz \
      > mapping/ex1.sam
    ```
2. Convert and coordinate-sort the SAM file to BAM format using `samtools`.

    ```bash
    samtools view -b mapping/ex1.sam |
      samtools sort -o mapping/ex1.sorted.bam

    samtools view -b mapping/ex2.sam |
      samtools sort -o mapping/ex2.sorted.bam

    samtools index mapping/ex1.sorted.bam
    samtools index mapping/ex2.sorted.bam
    ```
3. Initial mapping statistics can be obtained using `samtools flagstat`.

    ```bash
    samtools flagstat mapping/ex1.sorted.bam > mapping/ex1.flagstat.txt
    samtools flagstat mapping/ex2.sorted.bam > mapping/ex2.flagstat.txt

    samtools stats mapping/ex1.sorted.bam > mapping/ex1.stats.txt
    samtools stats mapping/ex2.sorted.bam > mapping/ex2.stats.txt
    ```

4. View the mapping statistics.

    ```bash
    cat mapping/ex1.flagstat.txt
    cat mapping/ex2.flagstat.txt

    grep '^SN' mapping/ex1.stats.txt
    grep '^SN' mapping/ex2.stats.txt
    ```
:::

Initial mapping showed a **strong difference in apparent human sequence content between the two extractions**. `ex1` had a very high mapping rate of **95.0%**, with approximately **28.5 million aligned bases**, whereas only **19.9%** of `ex2` reads mapped to chromosome 22, yielding approximately **1.14 million aligned bases**.

The proportion of properly paired reads was also substantially higher in `ex1` (**47.8%**) than in `ex2` (**3.1%**), indicating that paired-end alignments from `ex1` were much more often consistent with the expected relative orientation and placement of the two mates. In contrast, the very low proper-pair rate in `ex2` suggests that most reads either failed to map or did not form concordant paired-end alignments.

`ex2` additionally showed a markedly higher mismatch-derived error rate (**0.582%**) than `ex1` (**0.034%**). Taken together, these results indicate that `ex1` contains substantially more sequence consistent with the supplied human reference and provides far more usable human-aligned data than `ex2`. However, because only chromosome 22 was used as the reference, these mapping statistics should be interpreted as evidence of consistency with human origin rather than definitive proof of genome-wide human origin.
