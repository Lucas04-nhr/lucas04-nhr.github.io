## Part A: Exact Alignment Exercise {#exact-alignment-exercise}

Consider the text `ACGTAACGTAACGCANTAACG` and pattern `TAACG`.

::: info
I use $T$ for the text and $P$ for the pattern, and let $n$ be the length of the text $|T|$ and $m$ be the length of the pattern $|P|$.
:::

1.  What is the length of the strings, and what is the size of the alphabet?

    The text has length $n = 21$ and the pattern has length $m = 5$.

    The symbols occurring in the text are is $\Sigma = \{A, C, G, T, N\}$, so the size of the alphabet is $|\Sigma| = 5$.

2.  How many shifts and how many comparisons do we need for an exhaustive naive search?

    A pattern of length $m$ can start at $n - m + 1$ positions in the text, so we need $n - m + 1 = 21 - 5 + 1 = 17$ shifts. That is, there are **17 possible shifts/alignments**.

    If we exhaustively compare all $m = 5$ characters at every position, the number of character comparisons is $17 * 5 = 85$ comparisons. Thus the worst-case exhaustive naive search requires **17 alignments and 85 character comparisons**.

    If the implementation stops as soon as it encounters the first mismatch, the number for this particular sequence is much smaller. The three true matches each require 5 comparisons, while the remaining 14 windows differ already at the first character:

    $$
      3 \times 5 + 14 \times 1 = 29
    $$

    So an early-termination naive implementation performs only 29 character comparisons on this particular example, although its worst-case complexity remains $O(nm)$. The pattern occurs at zero-based text positions **3, 8, and 16**.

3.  Consider the Rabin–Karp algorithm and define a rolling hash function.

    We can treat a DNA string as a number in base 5, and define the character encoding as follows:

    ::: table title="DNA Character Encoding" align="center" copy="all"
| Character | Encoding |
| :-------: | :------: |
|     A     |    0     |
|     C     |    1     |
|     G     |    2     |
|     T     |    3     |
|     N     |    4     |
    :::

    For a length-$m$ string, we have: $S = s_0 s_1 ... s_{m-1}$, and we can define the hash function as:

    $$
      h(S) = \left( \sum_{j=0}^{m-1} v(s_j) \cdot 5^{m-1-j} \right) \mod 101
    $$

    where $v(s_j)$ is the integer encoding of character $s_j$.

    For the exercise, let $m = 5$, so we have

    $$
      \begin{aligned}
        h(S) & = h(s_0 s_1 s_2 s_3 s_4) \\
             & = \left( v(s_0) \cdot 5^4 + v(s_1) \cdot 5^3 + v(s_2) \cdot 5^2 + v(s_3) \cdot 5^1 + v(s_4) \cdot 5^0 \right) \mod 101
      \end{aligned}
    $$

    ::: note
    Use of the prime modulus 101 is to keep the hash values small while reducing collisions.

    For the pattern `TAACG`, we have the encoded values `3, 0, 0, 1, 2`, so the hash value is:

    $$
    \begin{aligned}
    h(P) & = (3 \cdot 5^4 + 0 \cdot 5^3 + 0 \cdot 5^2 + 1 \cdot 5^1 + 2 \cdot 5^0) \mod 101 \\
         & = (3 \cdot 625 + 0 + 0 + 5 + 2) \mod 101 \\
         & = (1875 + 7) \mod 101 \\
         & = 1882 \mod 101 \\
         & = 64
    \end{aligned}
    $$

    :::

4.  Explain why your hash function is a rolling hash function.

    The important property is that the hash of the next window can be computed from the previous hash without recomputing all five characters.

    Suppose we have a window $S = s_0 s_1 s_2 s_3 s_4$ with hash $h(S)$, and we want to compute the hash of the next window $S' = s_1 s_2 s_3 s_4 s_5$. We can derive the rolling hash as follows:

    ::: steps
    1. The old contribution of $s_0$ is $v(s_0) \cdot 5^4$. We can remove this from the hash by subtracting it.
    2. After removing it, all remaining characters shift one base-5 position to the left, which is equivalent to multiplying by 5.
    3. The new character $s_5$ is added to the hash.
       :::

    Therefore, we have:

    $$
      h_{i+1} = \left[ 5 \left( h_i - v(T_i) \cdot 5^{m-1} \right) + v(T_{i+m}) \right] \mod 101
    $$

    For $m = 5$, we have $5^{m-1} = 5^4 = 625$ and $625 \mod 101 = 19$

    So the practical update can be written as:

    $$
      h_{i+1} = \left[ 5 \left( h_i - 19 \cdot 5^{m-1} \right) + v(T_{i+m}) \right] \mod 101
    $$

    This requires constant time, $O(1)$, per shift rather than $O(m)$.

    That's why it is a **rolling hash**.

5.  Compute the hash of the pattern and the hash of each shift. Is your choice of hash function good?

    The pattern hash is $h(P) = 64$.

    The 17 text windows and their hashes are:

    ::: table title="Rabin–Karp Window Hashes" align="center" copy="all"
| Position | Window | Hash |
| -------: | :-----: | -----: |
| 0 | `ACGTA` | 89 |
| 1 | `CGTAA` | 41 |
| 2 | `GTAAC` | 10 |
| 3 | `TAACG` | **64** |
| 4 | `AACGT` | 38 |
| 5 | `ACGTA` | 89 |
| 6 | `CGTAA` | 41 |
| 7 | `GTAAC` | 10 |
| 8 | `TAACG` | **64** |
| 9 | `AACGC` | 36 |
| 10 | `ACGCA` | 79 |
| 11 | `CGCAN` | 96 |
| 12 | `GCANT` | 85 |
| 13 | `CANTA` | 33 |
| 14 | `ANTAA` | 70 |
| 15 | `NTAAC` | 48 |
| 16 | `TAACG` | **64** |
    :::

    Therefore, Rabin–Karp identifies the three candidate positions: **3, 8, and 16**.

    All three candidate strings are actually equal to `TAACG`, so there are **no hash collisions** in this example. The hash function is therefore good for this small data set.

    However, a hash function is not judged only by this one example. A good hash function should:
    - distribute possible strings approximately uniformly over the hash space;
    - have a low collision probability;
    - be fast to calculate;
    - support an $O(1)$ rolling update;
    - distinguish changes in both character identity and character position.

    For Rabin–Karp, a useful practical metric is the **collision rate**:

    $$
      P(h(X) = h(Y) \mid X \neq Y)
    $$

    If hashes are approximately uniformly distributed over \(q\) values, we would ideally expect the collision probability to be approx. $\dfrac{1}{q}$. In this example, we have $q = 101$, so the expected collision probability is $\dfrac{1}{101} \approx 0.0099$.

    A deliberately bad rolling hash could simply be:

    $$
      h(S) = \left(\sum_i v(s_i)\right) \mod 5
    $$

    It can still be rolled efficiently:

    $$
      h_{i+1} = \left(h_i - v(T_i) + v(T_{i+m})\right) \mod 5
    $$

    However, it ignores the order of the characters. For example, `ACGTA` and `TACGA`, as well as any permutation containing the same characters have the same hash value, even though they are different strings. This is a poor hash function because it has a high collision probability.

    Another extremely bad example is $h(S) = 0$, which is constant for all strings. It technically allows constant-time updates, but every window collides with every other window, so Rabin–Karp degenerates to naive matching.

6.  How many operations did the exhaustive search with the Rabin–Karp algorithm require?

    There are 17 candidate windows.

    Rabin–Karp first computes the hash of the pattern and the first text window. The remaining 16 window hashes are generated using the $O(1)$ rolling update.

    We therefore perform 17 hash comparisons:

    $$
      h(P) \stackrel{?}{=} h(T[i:i+5])
    $$

    Only three windows have the same hash as the pattern: 3, 8, and 16.

    Because a hash match is only a candidate match, Rabin–Karp must verify these strings explicitly. Each verification requires at most 5 character comparisons: $ 3 \times 5 = 15 $ comparisons in total.

    Thus, if we count hash comparisons and verification character comparisons, $17 + 15 = 32$ operations in total. They are required after the hashes have been constructed.

    If hash-generation operations are also counted, the accounting is slightly different:
    - compute pattern hash: $O(m)$;
    - compute first text-window hash: $O(m)$;
    - 16 rolling-hash updates: $O(16)$;
    - 17 hash comparisons;
    - 15 verification character comparisons.

    Thus the important complexity is not the exact constant number but $O(n + m)$, which is much better than the $O(nm)$ of naive matching.

7.  When is Rabin–Karp beneficial?

    Rabin–Karp is especially beneficial when the text is large and the pattern is long enough that repeatedly comparing every character would be expensive.

    Its main advantage is that most candidate positions can be rejected by comparing only two fixed-size hash values when

    $$
      h(P) \neq h(T[i:i+m])
    $$

    A character-by-character comparison is needed only when the hashes agree.

    It is particularly useful when:

    ::: steps
    1.  ==**Searching a long text or genome.**==

        After the first window hash is computed, each new position can be examined with an \(O(1)\) rolling update.

    2.  ==**Searching for many patterns of the same length.**==

        Their hashes can be stored in a hash table, and every text window can be tested against many patterns simultaneously.

    3.  ==**Exact matching is required.**==

        Rabin–Karp provides candidate matches efficiently, followed by exact verification.

    4.  ==**The hash function has a low collision rate.**==

        In the expected case, only true or rare accidental hash matches require full sequence comparison.

:::

For sequence analysis, this illustrates a broader motivation behind efficient alignment algorithms: real NGS analysis involves mapping large numbers of sequence reads to reference genomes, and a direct exhaustive comparison against every reference position would be computationally prohibitive. The course materials therefore introduce specialized high-speed aligners such as BWA and Bowtie rather than exhaustive string comparison.

## Part B: Next-generation Sequencing Exercise {#ngs-exercise}

### Background and Aim {#background-and-aim}

Ancient DNA (aDNA) is typically characterised by **short fragment lengths**, **low endogenous DNA content**, and **post-mortem nucleotide damage**, especially increased **C→T substitutions near the 5′ end** and complementary **G→A substitutions near the 3′ end**. PCR amplification can further reduce the effective information content of a sequencing library by generating duplicate reads.

The aim of this analysis is to compare two paired-end Illumina datasets, `ex1` and `ex2`, obtained from two DNA extractions of a human-like skeleton. The analyses are designed to determine:

1. whether the sequencing data are consistent with **human origin**;
2. whether the data contain molecular signatures consistent with **ancient DNA**;
3. which extraction should be prioritised for further downstream analysis.

#### Filter Alignments to Require at least 30 Aligned bp {#filter-alignments}

The assignment requires alignment-based analyses to retain reads with at least **30 bp aligned to the reference**.

The following AWK filter calculates aligned query/reference positions from the CIGAR operations `M`, `=` and `X`.

:::steps
1. Filter the BAM files to retain only reads with at least 30 aligned bases.

    ```bash
    samtools view -h dedup/ex1.dedup.bam |
    awk '
    BEGIN {OFS="\t"}
    /^@/ {print; next}
    {
      cigar=$6
      x=cigar
      aligned=0

      while (match(x, /[0-9]+[MIDNSHP=X]/)) {
        token=substr(x, RSTART, RLENGTH)
        len=token
        sub(/[A-Z=]/, "", len)
        op=substr(token, length(token), 1)

        if (op=="M" || op=="=" || op=="X")
          aligned += len

        x=substr(x, RSTART + RLENGTH)
      }

      if (aligned >= 30)
        print
    }' |
    samtools view -b -o dedup/ex1.dedup.min30.bam -
    ```

    ::: note
    This is the command for `ex1`. Repeat for `ex2`.
    :::

2. Index the filtered BAM files.

    ```bash
    samtools index dedup/ex1.dedup.min30.bam
    samtools index dedup/ex2.dedup.min30.bam
:::

### Conclusion {#conclusion}

The chromosome 22 alignments show that both datasets contain reads consistent with **human origin**, but this conclusion is limited to the reference sequence used and does not by itself prove that the reads are endogenous human DNA. `ex1` produced by far the greater quantity of usable sequence: it retained **379,990 reads** and **28.49 Mb** of aligned sequence after duplicate removal and the $\geqslant$30 bp filter, compared with **6,628 reads** and **0.392 Mb** for `ex2`. It also had much lower PCR duplication and a much higher properly paired rate. On yield and library complexity alone, `ex1` would therefore be the stronger dataset.

The molecular-authenticity evidence leads to a different conclusion. `ex2` combines a substantially shorter median fragment length with pronounced, complementary 5′ C→T and 3′ G→A terminal damage. Together, these are strong signatures of ancient DNA. `ex1` lacks detectable terminal damage and has a much longer fragment distribution, making it more consistent with modern or otherwise well-preserved human DNA. In the context of a skeleton expected to contain ancient DNA, the large quantity of undamaged human sequence in `ex1` should therefore be treated cautiously because it could reflect modern human contamination rather than authentic endogenous ancient DNA.

Accordingly, **`ex2` should be prioritised when the objective is to analyse authentic ancient DNA**, even though its low yield, high duplication, and very small number of concordant pairs severely limit downstream resolution. `ex1` may be useful for analyses requiring sequence depth, but it should not be preferred for ancient-genome inference without additional evidence demonstrating authenticity. A follow-up experiment should increase sequencing depth for `ex2`, include extraction and library blanks, and evaluate genome-wide mapping and contamination rather than chromosome 22 alone.

### Discussion {#discussion}

> Can the Data Be Identified as Artificial?

It would not be possible to determine with certainty from the sequence data alone that these are not real sequencing data. Features such as read length, base-quality scores, adapter contamination, PCR duplication, mapping errors, short fragments, and terminal nucleotide damage can all occur in genuine experiments, but they can also be reproduced by a sufficiently realistic simulator. Conversely, unusual values do not prove simulation because library preparation, target enrichment, contamination, reference choice, and previous processing can produce atypical datasets. Definitive evidence about provenance would require information independent of the reads, such as instrument run records, sample and library metadata, checksums from the sequencing facility, or appropriate experimental controls.

The data nevertheless contain strong reasons for suspicion under the stated experimental scenario. Most notably, approximately **95% of `ex1` reads mapped to chromosome 22 alone**. Chromosome 22 represents only a small fraction of the human nuclear genome, so such a high proportion would be highly unexpected for untargeted shotgun sequencing of a human sample. The approximately **19.9% initial chromosome 22 mapping rate for `ex2`** is also unusually high under that assumption. These observations would be compatible with reads generated from chromosome 22, a chromosome-specific enrichment experiment, or a dataset deliberately constructed for the assignment. The distinction cannot be resolved without knowing how the libraries were produced.

Other properties, including the nearly fixed 75 bp read length in `ex1`, its extremely low duplicate and mismatch rates, and the sharply contrasting damage profile introduced in `ex2`, may also make the pair appear educationally designed. However, none of these features is individually impossible in real data. Therefore, the most defensible conclusion is that the datasets are **consistent with artificial or curated teaching data and contain patterns that would be improbable for ordinary untargeted sequencing**, but their non-biological origin cannot be proven from the sequence files alone.

    For L30, the main change occurred during mapping. The mean GC content increased from 47.70% before mapping to 57.83% among mapped reads, which is essentially identical to the reference genome GC content of 57.81%. Applying the MAPQ $\geqslant$ 1 filter removed only 551 additional reads and caused almost no further change in the GC distribution. This suggests that most mapped L30 reads were already mapped unambiguously and with high confidence.

    L10 behaved very differently. All 133,000 reads were initially reported as mapped, so mapping alone did not change the GC distribution. However, after applying MAPQ $\geqslant$ 1, only 9,101 reads remained. The mean GC content of this retained subset dropped sharply from 47.64% to 19.76%.

    The L10 result shows that mapping-quality filtering can introduce a strong selection bias when reads are extremely short. Most 10 bp reads can match many positions in the reference genome and therefore receive MAPQ 0. The small subset that survives the MAPQ filter consists of sequences that happen to have fewer alternative matches, but this subset is not necessarily representative of the overall reference genome composition. In this dataset, these relatively unique 10 bp reads are strongly enriched for low-GC sequences, producing the very low mean GC content of 19.76%.

    Overall, the MAPQ filter has little effect on L30 because most mapped 30 bp reads are already unique and reliable, whereas it removes the vast majority of L10 reads and substantially changes their sequence composition.

7. For the *M. Leprae* genome we are using, what is the expected number of random hits with UP TO 2 mismatches for reads that are 10 and 30 bp long? With these estimates and the results from 6., what can you conclude about the reliability of the data in the two different fastq files (`L10.fq.gz`, `L30.fq.gz`). If you were to produce new data, what would be your strategy?

    For a random DNA read of length $k$, assuming an IID uniform sequence model, the probability of matching a given reference position with exactly $i$ mismatches is

    $$
      P(X=i)=\binom{k}{i}\left(\frac{1}{4}\right)^{k-i}\left(\frac{3}{4}\right)^i,
    $$

    because a random base matches the reference with probability $\dfrac{1}{4}$ and mismatches with probability $\dfrac{3}{4}$.

    Therefore, the probability of obtaining a match with up to two mismatches is

    $$
      P(X \leq 2) = \sum_{i=0}^{2} P(X=i) = \binom{k}{0}\left(\frac{1}{4}\right)^k + \binom{k}{1}\left(\frac{1}{4}\right)^{k-1}\left(\frac{3}{4}\right) + \binom{k}{2}\left(\frac{1}{4}\right)^{k-2}\left(\frac{3}{4}\right)^2.
    $$

    For a reference genome of length $L=3{,}187{,}112$ bp, the expected number of random hits is approx.:

    $$
          E = (L - k + 1) \cdot P(X \leqslant 2).
    $$

    The calculations were performed using:

    ```python
    import math

    L = 3187112

    for k in [10, 30]:
      p = sum(
        math.comb(k, i) * (1/4)**(k-i) * (3/4)**i
        for i in range(3)
      )

      expected = (L - k + 1) * p

      print(f"k = {k}")
      print(f"P(<=2 mismatches) = {p:.12g}")
      print(f"Expected random hits = {expected:.12g}")
      print()
    ```

    The results were:

    ::: table title="Expected Random Hits with Up to 2 Mismatches" align="center" copy="all"
| Read Length | $P(\leqslant 2\text{ mismatches})$ |  Expected Random Hits |
| :---------: | :--------------------------: | :-----------------: |
| 10 bp       |        $4.1580\times10^{-4}$ |             1325.20 |
| 30 bp       |       $3.4747\times10^{-15}$ | $1.11\times10^{-8}$ |
    :::

    The difference is extremely large. A random 10 bp read is expected to have approximately 1,325 positions in the *M. leprae* genome that match with at most two mismatches. In contrast, a random 30 bp read has an expected number of random hits essentially equal to zero.

    This explains the alignment results observed in the previous questions. All 133,000 L10 reads were reported as mapped, but most of them were highly ambiguous: 123,899 had MAPQ 0, and only 9,101 remained after filtering for MAPQ $\geqslant$ 1. In addition, L10 reads had many best and suboptimal hits. The theoretical expectation of more than one thousand random near-matches per 10 bp read shows that simply obtaining an alignment for such a short read provides very little evidence that the read truly originated from that genomic position.

    The 30 bp reads were much more reliable. Of the 133,000 original reads, 100,036 mapped, and 99,485 remained after requiring MAPQ $\geqslant$ 1. Their mapped GC content was approximately 57.83%, almost identical to the reference genome GC content of 57.81%. The negligible expected number of random 30 bp hits is consistent with the observation that most mapped L30 reads had a unique best hit and high MAPQ.

    Overall, the L10 dataset is not reliable for confident mapping to the reference genome because the reads are too short to provide sufficient sequence specificity. Even a positive mapping quality only identifies a small and highly selected subset of 10 bp reads, and the strong change in GC composition after filtering shows that this subset is not representative of the original data.

    The L30 dataset is substantially more reliable because 30 bp reads contain much more sequence information and the probability of a random near-match is extremely small.

    If producing new data, I would therefore use considerably longer reads rather than 10 bp reads. Longer reads would reduce the number of random and repetitive matches, increase the fraction of uniquely mapped reads, and improve mapping quality. In practice, I would choose a read length comfortably above 30 bp, subject to the biological material and sequencing protocol, so that the reads contain enough information for reliable alignment.
